MISSING-YEAR FIX IN THIS VERSION

The live question "What was Google's annual revenue?" caused the model to
choose 2023 and then 2025 in separate requests. The numbers matched the tool
evidence, so the output guardrail passed. The missing check was whether the
user had actually supplied a fiscal year.

New request_guardrails.py recognises explicit four-digit year mentions and
ascending ranges, such as FY2025 and 2023 through 2025. Before ANY lookup runs:
- No recognised fiscal year: Python returns the fixed request for a year,
  evidence [], guardrail not_applicable, checked_claims 0. A guessed model
  tool call cannot bypass this. There is only one model request in this path.
- A proposed year outside the recognised set: the whole batch is rejected
  with HTTP 502 and code request_guardrail_blocked. No financial lookup runs.
- Supported years: the existing lookup and evidence checks proceed.

Common dates such as 2025-12-31 do not count as fiscal-year requests. Relative
expressions (latest, last year), written-out years and abbreviated/reversed
ranges require clarification rather than an inferred default. Definitions do
not need a year because they do not request a financial lookup.

This is a narrow year-mention check, not complete question understanding.
A mentioned year can still be associated with the wrong company or measure,
and a model can omit a requested figure. Those are separate evaluation tasks.

HOW THE REQUEST WORKS

1. FastAPI accepts {"question": "..."} at /ask.
2. The first model request selects tool arguments or a fixed clarification/
   definition reply. Local validation rejects unknown companies or measures,
   invalid dates, noninteger years, duplicate calls and extra arguments.
   The request guardrail then checks all proposed years against explicit year
   mentions in the original question before any lookup runs.
3. Python executes at most six distinct cached lookups, in one tool round.
   Example: two companies x three years x one measure = six lookups.
4. A second model request proposes structured claims for successful results.
   Missing/conflicting/unsupported results must not have numerical claims.
5. The output gate repeats each requested lookup against the local cache and
   requires exact agreement with the evidence, including snapshot hashes.
   It then requires every successful result to have one matching AI claim.
6. Python builds the final English answer from the verified results, including
   source links. Unchecked AI prose is never returned as the answer.

There is no second tool round and no unbounded retry loop. At most two model
requests are made, each with a 30-second client timeout, zero automatic retries
and a 4,000-output-token ceiling. These are per-request controls, not an overall
account spending limit. Financial lookups and cache verification are local.

WHY THE CACHE CHECK WAS ADDED

The previous guardrail knew Microsoft's July-to-June calendar. A general tool
cannot validate every company by using that same fixed calendar. This version
compares each tool result with a deterministic lookup using the same requested
company, measure, year and cutoff against the cached source files.

This detects changed values, company/metric swaps, incorrect reporting periods,
altered links, incomplete evidence and fabricated not_found results, even when
the model copies the altered result. It also rejects a cache change between
lookup and answer verification. Avoid refreshing data while requests run; retry
after the refresh finishes if an in-flight request is blocked.

The check reuses the same lookup algorithm. It is not an independent audit of
the algorithm, accounting interpretation or original SEC data. A shared bug
or bad source data still requires source review and evaluation to uncover.
Hashes identify the bytes used; they are not proof of SEC authenticity.

WHAT "PASSED" DOES AND DOES NOT MEAN

guardrail passed means the returned numerical claims agree with the retrieved
results and the current local snapshots under our selection rules. Zero checked
claims is valid when all lookups returned missing/conflict/unsupported statuses.

The guardrail does not independently establish that the model understood every
part of the question or requested all required figures. For example, a model
could select the wrong supported metric; its evidence might still be internally
consistent. Live routing checks and the later labelled evaluation must assess
that separate property. Definitions and clarification choices also need testing.

SUPPORTED SCOPE AND KNOWN GAPS

Supported: configured company + annual revenue, operating income or net income
attributable to the parent + specified fiscal year, optionally with a filing-date
cutoff. A bare year is interpreted as the company's fiscal year; actual start
and end dates are included. Fiscal and calendar years are not interchangeable.

Not yet implemented: calculated margins, growth or differences; forecasts;
quarters; narrative filing retrieval; conversation memory; the full agent graph.
Requests requiring those features should receive a fixed unsupported response.

The configuration contains 15 distinct companies; only downloaded and supported
data is available. This update does not fix the previously documented gaps:
    AVGO FY2025 net_income: not_found under the parent-net-income definition.
    IBM FY2023–FY2025 operating_income: not_found under the supported tag.
    CRM FY2025 all three measures: conflicting annual-period labels.

No alternative accounting measure or calendar is silently substituted.

HTTP OUTCOMES

200: A verified answer, an explicit missing/conflict/unsupported data result,
     or a fixed clarification/definition/unsupported-request reply.
422: Invalid input or a model-generated batch exceeding six lookups.
503: Required local data is missing, unreadable or invalid. No final answer is
     produced. The response identifies the company and gives controlled guidance.
502: Model/provider failure, malformed tool calls, an unrequested fiscal year,
     or failed output verification.
     No unverified final answer is returned.

If a result is missing in a valid cache, that is not_found (200). If the cache
itself is missing, that is an operational data error (503), not evidence that
the company has no financial data.
